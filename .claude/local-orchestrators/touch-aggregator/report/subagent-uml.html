2Orchestration layout — orchestrator, task, plan, loop

The object model behind the skills pair: execute-research produces ONE plan, a divider partitions it by file ownership, and each sub-plan runs a gated loop. The pipeline first, then the objects and who owns what.

  • A Loop has no OS identity. It is a while closure inside the one CLI process (verified: one pid while six agents ran) — nothing to signal, nothing on disk. Its only observable trace is the journal, the findings files, and the monitoring events.
  • The findings file is the loop's real state. Attempt N+1 receives file paths, never inlined text — which is exactly why stop-and-restart-fresh works: the next attempt reconstructs everything it needs from disk.
  • Restart = journal replay. resumeFromRunId re-runs the script and serves completed agent calls from cache — replayed nodes are rendered "replayed, not re-executed", and cached agents' file edits are NOT re-applied to a dirty tree.
  • Never resume an agent. Both skills mandate a fresh subagent per attempt; the loop advances by spawning, never by continuing.

3Loop cycle — attempts and gates

One sub-plan's gated loop, as implement-plan defines it. Gates are read-only; only the implementer edits source, and only within its sub-plan's owned files.

stateDiagram-v2
    [*] --> Implement : attempt N, fresh implementer
    Implement --> TestGate : change-set ready
    TestGate --> Critique : green
    TestGate --> NextAttempt : red - findings file written
    Critique --> SubPlanDone : clean
    Critique --> NextAttempt : findings file written
    NextAttempt --> Implement : N+1, findings paths handed off
    NextAttempt --> Failed : N = MAX_ATTEMPTS
    SubPlanDone --> AggregateGate : all sub-plans green
    AggregateGate --> [*] : merged change-set green
    AggregateGate --> Implement : aggregate red - targeted fix loop
    Failed --> [*]
  • Stop lands between states. TaskStop aborts whichever agent is in flight; the loop's closure dies with the run. Restarting re-enters at Implement with the last findings files — never mid-attempt.
  • Touch renders the cycle from convention. Attempt numbers, roles, and gate names come from the [monitor] marker and findings filenames — dashed in the graph; spawn/finish times and tokens come from the harness — solid.

4Behavior — spawn, name join, stop

The two flows the orchestrator-skill discussion settled: naming works before creation via writable channels, and stop works only as a pull — the owned session acts on Touch's recorded intent; Touch never pushes into a running process.

    rect rgba(128,128,128,0.06)
    note over UI,FS: stop (model-mediated verb)
    UI->>AG: click Stop on Some_Name
    AG->>AG: append control.jsonl - state requested
    AG->>CC: type TaskStop instruction into PTY, gated on idle - state sent
    CC->>CC: TaskStop on Some_Name's task

    AG->>FS: observes the effect
    AG-->>UI: state confirmed - derived, never assumed

  • No push channel exists. A running interactive session has no socket, no port, no injectable TTY — the PTY Touch itself holds is the only input path, which is why controls exist only for owned sessions.
  • The control log is the only record of a stop. The harness writes nothing when a task is stopped, so a Touch-stopped agent is indistinguishable from a crash without control.jsonl — the audit wins over quiet-timeout inference.
  • requested → sent → confirmed are distinct UI states. Stop and restart are model-mediated; requested-but-unconfirmed is the normal failure mode, and the UI says so.

5Lifecycle — agent states

What the graph page may honestly assert about a node at each moment. There is no completion marker inside a transcript, so liveness is three-state, derived from idle time and the journal / parent tool_result.

stateDiagram-v2
    [*] --> Declared : plan / script names it
    Declared --> Queued : fan-out over concurrency cap
    Declared --> Running : spawn - meta.json written
    Queued --> Running : slot frees
    Running --> Finished : journal result / parent tool_result
    Running --> Unknown : idle 180s or more
    Unknown --> Running : activity resumes
    Unknown --> Superseded : watchdog respawn, new ordinal
    Running --> Stopped : TaskStop - Touch audit only
    Running --> Paused : hook gate holds at tool boundary
    Paused --> Running : gate released
    Finished --> [*]
    Stopped --> [*]
    Superseded --> [*]
  • Declared and Queued have zero disk footprint — they are rendered as declarations, visually distinct from observed states; declared ≠ started is normal (cap is min(16, cpus−2)).
  • Pause is a hook gate, not a suspend. A PreToolUse/SubagentStart hook holds its response, so pause takes effect at the next tool boundary; an agent mid-reasoning cannot be paused. Deterministic on owned sessions with the Touch hook pack (v1.5).
  • Superseded nodes come from the 180s stall watchdog, which respawns a logical node under a fresh agentId — same journal key, next ordinal; the prior node is closed as superseded, never left "running forever".
