Probed, not assumed

The empirical results the plan stands on

Mongo is deployable here today

pip install pymongo (4.17.0) works through the proxy; docker pull mongo:7 succeeds and the container runs. No host mongod exists and apt has no candidate.

Change streams don't work

db.watch() fails with error 40573 on the standalone mongod this environment produces — so Mongo can never sit on the live path. Verified independently by two researchers.

The sub-document _id trap

{s,n} and {n,s} insert as two distinct documents — BSON _id equality is field-order sensitive. Probed by three perspectives; every _id becomes a canonical string.

Token math was wrong in the docs

output_tokens GROWS across split records of one message.id (571 of 901 corpus ids differ) — inception's "usage is copied" is false. Only $max upserts converge; first-wins under-reports 2.8×.

28% of records have no uuid

74 of 267 lines in this session (8 of 12 record types) carry no uuid, and a content-hash key silently collapses 142 of 333 corpus-wide. Only the four harness uuid-bearing types key by uuid; the rest key positionally.

/clear splits agents across sessions

One agent transcript lives as 223 lines in one session dir and 2 lines in another, sessionId rewritten, meta lost — stitched only by the parentUuid chain. sessionId is never a grouping key for agents.

A dead Mongo stalls 30 s by default

Default server-selection timeout froze a poll-loop probe for 30.1 s. Client timeouts are pinned at 500 ms and all mirror I/O is queued off the critical path.

The unguarded default is dangerous

A plain docker run mongo:7 publishes an unauthenticated database on 0.0.0.0 holding unredacted transcripts. The plan mandates loopback bind + auth + 0600 credentials before any mirror code.

Your asks, dispositioned

What you asked for, in your words

"separate collections for separate session datas"

DECLINED — with this machine's numbers

7+ sessionIds for one project would mean 7+ collections, each duplicating indexes, and the sidebar becomes an N-collection scan. What you actually want — per-session isolation — is an indexed sessionId field on every document plus filtered queries. One collection per entity type, never per session.

"custom state into another mongodb colection" referencing mapped session agents

ADOPTED — exactly as asked

Custom state is its own collection pair: custom_state_events (append-only journal, file-WAL first — it's the one dataset not rebuildable from ~/.claude) plus a seq-guarded derived head, both referencing mirrored documents by refId. An earlier in-chat sketch that put it as a subdocument on agents is formally overturned.

"store information in which line subagent is located on original session file"

ADOPTED — as a validated cache

Identity is the spawn record's uuid + toolUseId; the line/offset is a fileHint validated against the file's identity and marked stale on mismatch — because the CLI rewrites transcripts in place, offsets can lie.

"hook to store all session infos in mongodb"

ADOPTED — via tailing, not a hook

No supported push hook exists in CLI 2.1.220. The ingest is the planned 250 ms stat-first tailer projecting into Mongo as a write-behind mirror; the result is the same, the mechanism is the one that actually exists.

What got decided

Ten new global decisions (GD-21 … GD-30)

  • GD-21

    Dependency policy: pymongo 4.17.0 is the one permitted runtime dependency, importable from exactly two modules, lazily — its absence degrades the mirror, never the app. (A working ~90-line stdlib wire client was proven as fallback, and rejected only because auth crypto shouldn't be hand-rolled.)

  • GD-22

    Mongo is a write-behind, fully rebuildable mirror. The in-memory reduction serves every live read; .touch/ JSONL stays the system of record; with Mongo down the live view is fully functional.

  • GD-23

    Collections persist observations only — never verdicts, never liveness. One server-side reducer derives state at read time; derived data is droppable and rebuilt by replay. The watcher fixes (R-08/R-09/R-13) are hard preconditions: this very run reproduced the fabricated-failed badge live.

  • GD-24

    One string-_id grammar via a shared canonicalizer, and one normative 15-collection table that supersedes both schemas sketched earlier in chat (resolving their contradictions: run_nodes, the - separator, live:/hist: session union).

  • GD-25

    The idempotency algebra: $max for numerics, $addToSet for sets, $setOnInsert for immutables, $inc forbidden. Acceptance = ingest the corpus normally, shuffled, and reversed → identical fingerprint and counts.

  • GD-26

    Upsert-only mirror with generation mark-and-sweep: rewound records are retracted, never deleted — the mirror exists because the CLI destroys history, so it must not re-import that destruction. No TTL index, ever.

  • GD-27

    Security: loopback-only bind, mandatory auth, credentials in .touch/mongo.json mode 0600, refusal to mirror into a user-less mongod, derived database names, port never published.

  • GD-28

    "Custom state" defined once as a closed taxonomy (mirrored fact / derived / orchestration state / Touch application state) with a mandatory provenance field — custom state can never masquerade as harness fact.

  • GD-29

    Writer topology: agents only ever append to files; the aggregator is the sole Mongo writer, guarded by a writer lease. No credential in any prompt, no network in any agent.

  • GD-30

    The latency budget as numbers: ≤400 ms p95 action-to-pixel; Mongo contributes 0 ms to the critical path (bounded queue, circuit breaker, drops counted); per-tick ingest cost is O(bytes appended), asserted by test.

The plan also repairs its own foundations: the normative plan's "D8" row conflated two different decisions (the stack pin vs the journal-result rule) — split into D8.1/D8.2 and fixed at the source (R-38). Requirements provenance is pinned to the six decisive message uuids across both sessions, so implement-plan never re-reads a transcript.

The road

21 items in five phases (R-38 … R-58)

  1. Anchors, writers, lifecycle, fixtures

    R-38 … R-41, R-58

    Doc anchor repairs and measured-truth corrections; the writer-attribution w field; watcher self-exit protocol (three orphaned watchers are running right now); freezing the cross-session and retry fixtures before the retention sweep eats them. R-58 (added by user directive) pulls the fabricated-FAILED-badge fix — normative R-08/R-09/R-13 — into this pass's first wave and proves it by replaying the real streams: zero failed badges on research or synthesis plans, and the corrective done-after-failed history resolves last-event-wins.

  2. Foundations

    R-42 … R-45

    The hardened deployment recipe; the ref_key canonicalizer; the collection/index/validator layer with the shuffled-ingest acceptance test; the mirror engine — queue, breaker, lease, cursors, generation sweep, --rebuild and --backfill.

    gate: normative R-01…R-03 done; R-08 + R-09 + R-13 green

  3. Mirror pipelines

    R-46 … R-51

    Sessions as a tagged live/hist union; the 12-type record bucketing; agent fragment assembly across /clear splits; runs and nodes with derived timestamps and the run-level stop join; $max usage docs; the legacy events mirror plus artifact registry.

  4. Custom state

    R-52 … R-53

    The WAL-first custom-state collection pair, and slots — the name↔agentId binding with a pending / bound / orphaned / conflict state machine, so state written before spawn finds its agent after.

  5. Reduce, serve, accept, document

    R-54 … R-57

    The single reducer with read-time liveness; bounded WS replay with resume and live/backfill frame marking; the three-arm end-to-end acceptance (no-mongod, mirror, budget); run recipes and user-facing dispositions in the docs.
