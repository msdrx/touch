touch / ops design / restart & recovery

Restart mechanism — the full flow

Every path from a dead machine back to a live dashboard, as the touch-mongo-live plan legislates it. Files are the WAL, Mongo is a rebuildable projection, daemons die on purpose, and exactly one decision stays human. Node shapes: trapezoid = a command someone types, diamond = decision, rounded = system state.

automatic · self-healing manual · human or orchestrator guard · designed refusal

1The map — boot to steady state

The end-to-end restart flow. The left spine is the process bring-up (the only manual part); everything hanging off it is automatic once a process exists. Note the dotted edge: the live view never waits for Mongo.

  • The only mandatory manual steps are process launches. docker start touch-mongo (until the recipe carries --restart unless-stopped) and one command for the server. No data command exists in the happy path.
  • Recovery has no "recover" button. Watermark replay runs on every aggregator start; a full second pass over the corpus is a 0.16 s idempotent no-op, so replaying too much is free by construction (GD-25).
  • Two refusals are features: the mirror refuses a zero-user mongod (GD-27), and --backfill refuses timestamps newer than source mtime — both stop silent corruption at the door.

3Mirror self-heal loop — breaker and watermark

Inside aggregator/mirror.py (R-45). The poll loop never blocks on the database; failure trips a breaker, the breaker probes, and the cursor watermark guarantees nothing is skipped or double-counted while Mongo was away. Health simply narrates this loop.

flowchart LR
    POLL["poll tick
read new WAL lines"] --> Q["bounded queue
write-behind, non-blocking"]
    Q --> W{"upsert batch ok?"}
    W -->|"yes"| CUR["advance cursor

    CUR --> HOK["health: ok"] --> POLL
    W -->|"no"| N{"failures >= N?"}
    N -->|"not yet"| RS["retry next tick"] --> POLL
    N -->|"yes"| BRK["breaker OPEN
30s hold - health: degraded"]
    BRK --> PROBE{"probe connect ok?"}
    PROBE -->|"no"| BRK
    PROBE -->|"yes"| CATCH["watermark catch-up replay
from file store"] --> CUR

  • The database is never on the liveness path (GD-20 extension): a dead mongod costs one tick's budget, never a stall — the dead-port test pins tick duration under one tick budget.
  • Watermark, not memory: the resume point is the stored (stream, seq) cursor, so a crash inside the loop replays a suffix idempotently rather than trusting anything in RAM.

4Daemon lifecycle — designed death

R-40. Watchers and the mirror daemon are per-run processes: they end themselves when the run ends. "Nothing running after a finished run" is the correct steady state — the orphan-watcher defect (CONVO-14) is why. Only mongod and the monitor server are candidates for always-on supervision.

stateDiagram-v2
    [*] --> Running : driver starts daemon with ORCH_STATE_DIR
    Running --> Running : journal + events activity
    Running --> Closing : terminal orchestrator complete lands
    Closing --> SelfExit : journal quiet >= N s
    Running --> Stopped : driver epilogue stops daemons
    Running --> Killed : OS reboot / crash
    Killed --> Relaunched : only if a run is being resumed
    Relaunched --> Running : same protocol, fresh process
    SelfExit --> [*]
    Stopped --> [*]
  • Self-exit needs BOTH conditions — a terminal complete event AND sustained journal quiet — so a slow run is never mistaken for a finished one.
  • After a reboot, daemons come back only with a resumed run. Reviving a watcher for a task that is not running would tail nothing and recreate the orphan problem.

5Resuming an in-flight run — the one human decision

From plan/RESUME.md. Everything here is deliberately manual: cached agents' file edits are not re-applied to a dirty tree, so whether to resume, and from where, is a judgment call the system refuses to make alone.

flowchart TD
    DIED(["session, uplink or OS died mid-run"]) --> HC[/"health check: tail events.jsonl + journal.jsonl"/]
    HC --> ALIVE{"fresh token ticks?"}
    ALIVE -->|"yes"| NOOP(["run is alive - touch nothing"])
    ALIVE -->|"no"| SESS{"original session still exists?"}
    SESS -->|"yes"| TSTOP[/"TaskStop the old task"/]
    TSTOP --> RESJ[/"Workflow resumeFromRunId"/]
    RESJ --> CACHE["journal cache replays finished agents
cached = replayed, NOT re-executed"]
    CACHE --> CONT["first incomplete agent runs live
attempt state re-read from findings files"]
    SESS -->|"no - fresh session"| READJ[/"read journal.jsonl: which sub-plans closed green"/]
    READJ --> SKIP[/"edit script: skip green sub-plans"/]
    SKIP --> FRESH[/"launch fresh run of the same script"/]
    FRESH --> IDEM["implementers verify against the tree
gates are idempotent - green stays green"]
    CONT --> WD[/"restart watcher with ORCH_STATE_DIR
update orch-config wf_dir"/]
    IDEM --> WD
    WD --> DONE(["monitor replays full history
nothing observed is lost"])

    classDef auto fill:#0e7b8626,stroke:#3d9aa4
    classDef manual fill:#a85e1226,stroke:#b97a35
    class CACHE,CONT,IDEM,DONE auto
    class HC,TSTOP,RESJ,READJ,SKIP,FRESH,WD manual
  • Never resume blindly from a new session. resumeFromRunId is same-session only; a fresh session replaying the script would re-run agents whose edits are already in the tree. The journal tells you what closed — skip it, don't repeat it.
  • Findings files are the loop's real state: attempt N+1 rebuilds everything from disk, which is exactly why stop-and-restart-fresh is always safe at a loop boundary.
  • The resume pointer is durable: orch-config.json carries resume_from_run_id and wf_dir, so the procedure works from any future session in this repo.
